# Raspberry Pi OS Lite + Net-SNMP での最小リソース設計メモ

## 1. 結論

Raspberry Pi OS Lite 上で Net-SNMP と軽量アプリを運用する場合、最小構成の目安は次のとおり。

- ストレージ: 8 GB で最小動作可、16 GB が現実的な推奨、32 GB が余裕
- メモリ: 512 MB は厳しい、1 GB が実用的、2 GB が安心
- CPU: SNMP の通常ポーリング自体は軽い。ボトルネックは OID 数、ポーリング頻度、アプリ処理の負荷

最適化の基本は、OS から最小化し、Net-SNMP の公開範囲を絞り、アプリの責務を分離すること。

一般的には `apt` で Net-SNMP を入れるのが最も安定するが、ソースからの機能削減インストールやクロスコンパイルも可能。とはいえ、運用コストとメンテナンスコストが大きくなるため、実務上は「apt + 最小設定」が現実的。

## 2. リソース見積もり

### 2.1 ストレージの目安

- Raspberry Pi OS Lite 本体: 約 2〜4 GB
- Net-SNMP: 約 10〜80 MB
- アプリ本体と依存関係: 50 MB〜500 MB 程度
- ログ、パッケージキャッシュ、構築作業物: 1〜3 GB
- 実運用目安: 8 GB で動作可能、16 GB 推奨、32 GB が余裕

### 2.2 メモリの目安

- OS Lite 基本負荷: 約 150〜300 MB
- Net-SNMP: 約 10〜30 MB
- アプリ: 20〜200 MB 程度
- 合計目安: 256 MB は厳しい、512 MB はギリギリ、1 GB が実用的、2 GB が安心

### 2.3 処理速度の目安

- SNMP の定期ポーリングは通常 CPU 負荷が低い
- 典型的には数 % 未満〜10 % 程度の CPU 占有率が目安
- LAN 内応答時間は通常 10〜200 ms 程度
- OID 数が多い、poll が高速、walk が大きいと数百 ms まで増える可能性がある

### 2.4 モデル別の見立て

- Pi Zero / Pi 2 系: 512 MB〜1 GB 推奨、厳しめ
- Pi 3 / Pi 4: 1 GB〜2 GB 推奨、実運用に適する
- Pi 4 は負荷が軽い場合に最も扱いやすい

## 3. 最適化施策の整理

### 3.1 OS での最適化

- Raspberry Pi OS Lite を採用する
- 不要サービスを停止する
  - 例: `avahi-daemon`, `cups`, `bluetooth`, `triggerhappy`
- ログに対する抑制を行う
  - `journalctl` / `journald.conf` の `SystemMaxUse` を小さくする
- `/tmp` と `/var/log` を `tmpfs` にする
- `apt` cache を定期的に削除する
- `__pycache__` やビルド成果物を削除する

### 3.2 SNMP での最適化

- `snmpd.conf` で公開する OID を最小化する
- ポーリング間隔を長くする
- `getbulk` / `walk` の回数とサイズを削減する
- OID 数を増やしすぎない
- 監視データの集約と前処理で負荷を抑える
- 監視エージェントとアプリの責務を分離する

### 3.3 アプリ側の最適化

- Python で必要最小限の依存のみを使う
- `venv` を使って依存を閉じる
- `pip install --no-cache-dir --no-compile` を使う
- 非同期 I/O とバッチ処理を使って負荷を分散する
- キャッシュは必要最小限に留める

### 3.4 ストレージ削減の実務例

- 16 GB SD を推奨構成にする
- `/var/log` を `tmpfs` または別ボリュームへ切り出す
- `apt` キャッシュや一時ファイルを定期削除
- `/tmp` をメモリ上に置く
- ビルド時の中間ファイルやデバッグログを残さない

### 3.5 スループット維持の実務例

- オンデマンドでのポーリングを減らす
- 監視データの集約・前処理を行う
- 一度に大量の OID を取得しない
- 監視の負荷が高い場合は分散監視構成に切り替える

## 4. 優先順位

1. 不要サービス停止 + ログ抑制 + OID 絞り込み
2. tmpfs とキャッシュ削除
3. ポーリング間隔と問い合わせ数の見直し
4. アプリの非同期化とバッチ処理
5. 重い処理を別サーバーへ分離

## 5. Net-SNMP の apt インストールと最小化

### 5.1 一般的なインストール

```bash
sudo apt update
sudo apt install -y net-snmp net-snmp-utils
sudo systemctl enable --now snmpd
```

### 5.2 最適化の観点

- `ldd /usr/sbin/snmpd` で依存ライブラリを確認する
- 依存が多い場合は、機能削減と設定絞り込みが必要
- `snmpd.conf` を最小構成にする

### 5.3 最小設定例

```conf
# /etc/snmp/snmpd.conf
agentAddress udp:161
rocommunity public 192.168.1.0/24
view   systemonly  included   .1.3.6.1.2.1.1
view   systemonly  included   .1.3.6.1.2.1.25.1
access systemonly "" any noauth exact systemonly none none
```

- 監視対象が少ないなら、必要な OID だけ残す
- 可能ならローカルのみ、または管理ネットワークだけ公開にする

## 6. ソースビルドとクロスコンパイルの考え方

### 6.1 可能か

- Net-SNMP はソースからビルド可能
- ただし、Raspberry Pi OS Lite では `apt` インストールが圧倒的に簡単で安定する

### 6.2 役立つ場合

- 必要な機能だけ残したいとき
- 監視機能を最小構成にしたいとき
- 独自環境に合わせて機能削減したいとき

### 6.3 典型的な機能削減の例

```bash
./configure --prefix=/opt/net-snmp \
  --disable-manuals \
  --disable-scripts \
  --disable-debug \
  --disable-embedded-perl \
  --disable-perl-cc-check
make -j$(nproc)
make install-strip
```

- これでバイナリと依存を最小化しやすい
- ただし動作に必要な機能が消えるリスクがある
- 実運用では「apt を使うか、それとも自前ビルドするか」の判断が必要

### 6.4 実用的な判断

- ほぼすべての用途では `apt + 構成最適化` の方が安全で現実的
- ソースビルドは「極限まで小さくしたいとき」に限るべき

## 7. 共有ライブラリの問題

- `ldd /usr/sbin/snmpd` で依存の確認が重要
- 依存が多い場合は以下を整理する
  - 必要なライブラリだけを残す
  - 不要な Perl モジュールやプラグインを除去する
  - 静的リンクと動的リンクのトレードオフを比較する
- 実際には Pi の環境では「動的リンクの依存を最小化しつつ、必要最小限の機能だけを有効にする」ことが最も現実的

## 8. そのまま Python を使う場合の最適化

- Python で拡張 MIB ハンドラを作る場合、以下が有効
  - `venv` を使って依存を閉じる
  - `pip install --no-cache-dir --no-compile` を使う
  - `__pycache__` を削除する
  - 実行時に読む設定を最小化する
  - 低メモリ構造を使う
  - バッチ処理化して、突発的な負荷を抑える

### Python 実行の最適化例

```bash
python3 -OO -m venv /opt/mibenv
. /opt/mibenv/bin/activate
pip install --no-cache-dir --no-compile somepackage
```

- ただし Python はランタイム自体が重いので、軽いアプリでないと効率が落ちる
- 監視用ハンドラだけなら Python でも十分使えるが、長期安定性とメモリ効率に制約がある

## 9. Python を廃止して別言語に切り替える提案

### 9.1 Go の提案

- Go はバランスが良い
- 1 バイナリで動作し、依存が少ない
- 並列処理が得意
- メモリ効率が良い
- コーディング体験は Python より厳密だが、実運用では安定する

#### Go の最小ビルド例

```bash
go build -ldflags="-s -w" -trimpath -o /opt/mib-agent/mib-agent ./cmd/mib-agent
```

- `-s -w` でデバッグ情報を落とし、オーバーヘッドを減らす
- `trimpath` でビルド経路を隠す
- 1 バイナリ化すれば、配置と運用が簡単になる

### 9.2 Rust の提案

- 省メモリ・高スループットに強い
- ただし、開発体験は Python / Go より厳しい
- 経験があるなら選択肢になる

### 9.3 C の提案

- 最高速、最小メモリ
- ただし開発負荷が大きく、保守性が低い
- 小規模の監視エージェントならありだが、長期運用には向かない

### 9.4 結論

- コーディング体験を重視しつつ低メモリ化を狙うなら Go が最も適切
- Python で作っても不可能ではないが、長期的には Go への移行が有利
- Rust は経験があれば強いが、初期導入コストが大きい

## 10. 実務向けのおすすめ構成

- Raspberry Pi OS Lite を採用
- Net-SNMP は `apt` で最小構成インストール
- `snmpd.conf` は必要な OID のみ公開
- ログと一時データを抑制
- `/tmp` を `tmpfs` にする
- アプリは Go で 1 バイナリ実行
- SNMP ハンドラとアプリ処理を分離
- 監視を必要最小限に制限

### 推奨構成の目安

- 16 GB SD / 1 GB RAM: 実用的な推奨構成
- 32 GB SD / 2 GB RAM: 余裕のある構成
- 8 GB SD / 512 MB RAM: 最小構成（厳しめ）

## 11. 最終判断

- 「手軽さと安定性」を重視するなら: `apt + 最小設定 + ログ抑制 + OID 指定`
- 「さらに小さくする」なら: Net-SNMP のソースビルドと機能削減
- 「開発体験もある低リソース設計」を目指すなら: Go で MIB ハンドラを 1 バイナリ化
- Python のままでも十分に実用可能だが、メモリと実行体験の面では Go へ寄る方が有利

## 12. まとめ

- 最も実用的なのは、「apt で Net-SNMP を入れて、設定と監視対象を極端に絞る」こと
- さらに小さくしたい場合は、ソースビルドで機能削減することは可能だが、現実的には運用コストが高い
- 低メモリ・省リソース・高スループットを目指すなら、言語選択の見直しとして Go が最も現実的な実装選択
- 監視プロトコルの本質は「必要な OID だけを速く返す」ことなので、設計の最適化が最も効果が大きい

これが、今回の検討結果の総まとめである。
